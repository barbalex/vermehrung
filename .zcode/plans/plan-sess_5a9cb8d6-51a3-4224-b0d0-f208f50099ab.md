# New `bedarf` table: culture-level demand per year (issue #151)

WatermelonDB can't rename fields or tables, so as you said: new table `bedarf`, migrate event data into it server-side, then deactivate the event UI. The 5 new export columns are a separate follow-up step once this structure exists.

## Table design

`bedarf`, modeled on `event` (source: issue text + Seraina's field list):

| column | type | notes |
|---|---|---|
| `kultur_id` | string, indexed | belongs_to kultur |
| `person_id` | string, indexed | «Wer» — for follow-up questions |
| `jahr` | number, indexed | year the demand is for (Seraina: exact date not needed) |
| `beschreibung` | string, indexed | the demand itself: «Samen», «Knöllchen», «Töpfe», «50-100» … (name mirrors event form, per Seraina's screenshot) |
| `bemerkungen` | string | «Bemerkungen AV» |
| `neues_material` | string | «Neues Material liefern» for that year |
| `changed`, `changed_by`, `_rev`, `_parent_rev`, `_revisions`, `_depth`, `_deleted`, `_conflicts` | standard | revision system, same as every table |

Deliberately **no** `geplant` (obsolete once demand has a year, per Seraina) and **no** `teilkultur_id` (demand is culture-level).

## 5. Server (versioned in repo, applied operationally)

28. `src/sql/createTables.sql` — `bedarf` + `bedarf_rev` (mirror the event tables incl. `_rev_at` + indexes)
29. New `src/sql/createRevTriggers_bedarf.sql` (copy of the event trigger file, renamed)

31. New `src/sql/one-offs/2026-10-20_migrate_events_to_bedarf.sql`, two clearly separated phases:
    - **Phase A:** insert one rev-1 row into `bedarf_rev` per non-deleted event — same `id`, `kultur_id` (coalesced via teilkultur's kultur when null), `person_id`, `beschreibung`, `jahr = extract(year from datum)`, `_depth 1`, `_rev '1-'||md5(...)`, `_revisions ARRAY[_rev]`. The trigger materializes `bedarf`. `bemerkungen`/`neues_material` start empty (events have no such data)
    - **Phase B:** soft-delete all events (child deletion revs into `event_rev`), so every client sees them disappear via sync

## 6. Deployment order

1. Apply DDL + trigger to Postgres → 2. apply Hasura metadata, reload → 3. run Phase A, verify → 4. run Phase B → 5. deploy frontend (client-side schema v9 migration creates the local table; the bedarf subscription pulls migrated rows).
